# AgenticArxiv 面试准备

_围绕项目架构、上下文与记忆、工具调用、超时治理和可观测性的面试问答手册。_

---

## 📋 一句话介绍

AgenticArxiv 是一个面向 arXiv 论文检索、下载与中文翻译的可观测 Agent 工作台。项目重点不只是调用工具，而是将 ReAct 推理循环、工具调用协议、业务状态和评测指标解耦，支持在统一任务集上比较不同 Agent 实现。

## ⚙️ 技术流程

```text
用户自然语言任务
  → FastAPI /chat 接收请求
  → 根据 agent_type 选择 Agent（regex / MCP / skill_cli）
  → BaseAgent 注入会话上下文（已有论文、最近操作论文）
  → 组装 Prompt（任务 + 工具说明 + 历史轨迹）
  → LLM 决策 Thought + Action
  → 服务端校验并执行工具
  → 生成 Observation
  → 持久化轨迹、耗时，并用 SSE 实时推送
  → FINISH / 报错 / 达到最多 5 轮后结束
  → 前端展示结果、论文资产、翻译任务和历史日志
```

业务主链路：

```text
检索论文 → 选择或引用论文 → 下载 PDF → 异步翻译 → SSE 推送进度 → 查看或下载资产
```

翻译不会阻塞聊天。Agent 创建翻译任务后即可结束当前对话；后台任务继续下载、翻译，并通过 SSE 推送进度和最终状态。

## 🔧 三种 Agent 方案

| 方案 | 工具调用方式 | 面试表达 |
| --- | --- | --- |
| `regex` | LLM 输出 JSON，当前进程直接调用工具 | 最轻量，调用链短，但依赖模型稳定遵守格式 |
| `mcp` | 通过 stdio 的 MCP JSON-RPC 调用子进程 | 协议化、工具可发现、隔离更好，但有异步桥接复杂度 |
| `skill_cli` | LLM 依据 Skill 文档生成受限 CLI 命令 | 工具能力文档化，Token 更低；通过白名单和参数数组避免直接执行模型 Shell |

三种模式只替换工具描述、响应解析和调用通道；ReAct 循环、会话状态、翻译、日志和 SSE 都复用同一个 `BaseAgent`。因此 Benchmark 对比的是协议差异，而不是三套不同的业务实现。

## 💾 数据库字段与设计意图

项目当前使用 SQLAlchemy 管理 7 张核心表。数据库并非只保存最终答案，而是覆盖会话记忆、文件资产、异步任务和 Agent 执行轨迹，使一次任务在服务重启后仍能查询和复盘。

```text
sessions ──< session_papers
    │
    ├──< chat_logs ──< agent_steps
    │
    └──< translate_tasks

session_papers.paper_id ──> pdf_assets.paper_id
                         └─> translate_assets.paper_id
```

这里的关系主要通过业务键 `session_id`、`msg_id` 和 `paper_id` 关联；当前 ORM 没有声明数据库级外键。这让演示版本的表结构与清理逻辑较轻，但生产环境若需要强一致性和级联清理，应增加外键约束、唯一约束与迁移脚本。

### 1. 会话与短期记忆

| 表 | 核心字段 | 设计意图 |
| --- | --- | --- |
| `sessions` | `session_id`、`last_active_paper_id`、`last_active_at`、`updated_at` | 一个会话一条记录；保存最近操作的论文，支持“刚才那篇”的指代。`session_id` 唯一且有索引。 |
| `session_papers` | `session_id`、`paper_id`、`title`、`authors`、`summary`、`pdf_url`、`categories`、`position`、`created_at` | 保存某次检索的论文快照；`position` 让“第 1 篇”可稳定解析，`(session_id, position)` 有联合索引。`authors`、`categories`、`links` 以 JSON 文本保存。 |

会话论文有 60 分钟 TTL。这样可以避免历史论文长期占用 Prompt，也降低用户后续引用到过期搜索结果的概率。

### 2. PDF 与翻译资产

| 表 | 核心字段 | 设计意图 |
| --- | --- | --- |
| `pdf_assets` | `paper_id`、`pdf_url`、`local_path`、`status`、`size_bytes`、`sha256`、`downloaded_at`、`error` | 每篇论文一份原始 PDF 缓存；`paper_id` 唯一且有索引。`sha256` 用于完整性校验，`error` 保存失败原因。 |
| `translate_assets` | `paper_id`、`input_pdf_path`、`output_mono_path`、`output_dual_path`、`status`、`service`、`threads`、`translated_at`、`error` | 每篇论文一份翻译产物状态；区分单语与双语 PDF，保存翻译服务和线程数，便于复现性能配置。 |

这两张表体现“资产状态”和“任务状态”分离：资产表描述当前可用文件，任务表描述一次后台执行过程。一次翻译失败不会抹去已有的成功资产。

### 3. 异步翻译任务

| 表 | 核心字段 | 设计意图 |
| --- | --- | --- |
| `translate_tasks` | `task_id`、`session_id`、`paper_id`、`status`、`progress`、`input_pdf_url`、`input_pdf_path`、`output_pdf_path`、`meta`、`error`、`created_at`、`updated_at` | 一次翻译请求一条记录。`task_id` 唯一且有索引，`session_id` 有索引，便于按会话查询进度。`progress` 支持 SSE 实时展示，`meta` 用 JSON 文本承载可扩展配置。 |

典型状态流转：`PENDING → RUNNING → SUCCEEDED`；失败时进入 `FAILED` 并写入 `error`。该设计让前端能够先获得 `task_id`，随后独立订阅进度，而不用长时间阻塞 `/chat` 请求。

### 4. 对话与 Agent 轨迹

| 表 | 核心字段 | 设计意图 |
| --- | --- | --- |
| `chat_logs` | `msg_id`、`session_id`、`role`、`content`、`model`、`agent_type`、总耗时、Token、`termination_type`、`created_at` | 保存用户输入和 Agent 最终回复。`msg_id` 唯一且有索引，`session_id` 有索引；Assistant 消息还保存任务级性能与终止原因。 |
| `agent_steps` | `msg_id`、`step_index`、`thought`、`action_name`、`action_args`、`observation`、LLM/工具耗时、单步 Token、`created_at` | 保存一次消息内部的逐步 ReAct 轨迹。`action_args` 为 JSON 文本；步骤级耗时和 Token 用于定位性能与成本瓶颈。 |

`chat_logs` 与 `agent_steps` 通过 `msg_id` 关联：前者回答“用户问了什么、最终答了什么”，后者回答“中间如何决策、调用什么工具、每步花了多久”。

### 5. Token 与终止状态可观测性

运行时累计 `prompt_tokens`、`completion_tokens` 和 `total_tokens`。单步 Prompt/Completion Token 写入 `agent_steps`，任务级 Token 与 `total_time_ms`、`total_llm_ms`、`total_tool_ms`、`framework_overhead_ms` 一起写入 Assistant 对应的 `chat_logs`。同时记录 `COMPLETED`、`CANCELLED`、`MAX_ITERATIONS` 或 `ERROR`，避免只凭最终文本猜测任务是否正常结束。

当前 `/chat` 的响应模型没有直接返回 Token 明细，但日志查询和 Benchmark 可以读取这些字段。后续可将任务级指标加入 `/chat` 响应或单独提供运行详情接口，使前端、日志页和 Benchmark 使用同一指标口径。

## 📚 Prompt 与轨迹记录

每轮 Prompt 的核心结构如下：

```text
你是 AI 研究助手。
可用工具：检索、下载 PDF、异步翻译、查询缓存。
当前任务：{用户任务 + 会话上下文}
要求：
- 每轮只能调用一个工具
- Action 必须是严格 JSON
- 指代“刚才那篇”时使用 ref = null
- 翻译是异步任务，创建后直接 FINISH，不轮询
历史轨迹：
Thought / Action / Observation
```

一次完整执行建议记录以下字段：

| 阶段 | 记录内容 |
| --- | --- |
| 输入 | `session_id`、用户任务、Agent 类型、模型 |
| Prompt | 实际发送 Prompt、工具描述、上下文摘要 |
| 每一步 | `step_index`、Thought、Action、Action args、Observation |
| 性能 | 单步 LLM 耗时、单步工具耗时、总耗时、框架开销 |
| 成本 | `prompt_tokens`、`completion_tokens`、`total_tokens` |
| 结果 | 工具调用序列、终止原因、成功或失败、任务与资产 ID |

## 🔍 真实服务观测样本

测试会话：`interview-trace-20260828`。

- 输入：`检索最近 1 天 cs.LG 方向的论文，最多 1 篇。`
- Agent：`regex`
- 模型：`ep-20260820165946-646cn`
- 结果：成功返回 1 篇论文，并正常 `FINISH`
- 论文：*Learning a Continuous Sepsis Severity Score Without Hour-by-Hour Supervision: A Two-Site Retrospective Study*

真实轨迹：

| Step | Thought / Action | LLM 耗时 | 工具耗时 |
| --- | --- | ---: | ---: |
| 1 | 判断需要检索；调用 `get_recently_submitted_cs_papers(max_results=1, days=1, aspect=LG)` | 9,344 ms | 5,563 ms |
| 2 | 判断任务完成；`FINISH` | 10,374 ms | 0 ms |

汇总：

- 任务端到端耗时：约 25.3 秒
- LLM 累计耗时：19.72 秒
- 工具累计耗时：5.56 秒
- 工具调用准确：是
- 终止状态：正常 `FINISH`
- SSE：实时收到两条 `agent_step` 事件，与数据库日志一致

这条历史样本生成时，Token 持久化链路尚未补齐，因此无法从旧记录恢复本次真实 Token，不能将缺失值误报为 0。当前版本已经把单步和任务级 Token 写入数据库，但不会反向补全旧数据。

## 🎓 Agent 开发高频面试问答

回答时建议遵循“先讲结论，再讲项目实现，最后讲限制与改进”的顺序。这样既能说明做过什么，也能体现没有把 MVP 描述成生产级系统。

### 上下文管理

#### Q1：上下文管理和记忆管理有什么区别？

**答：** 上下文是某一次 LLM 调用实际看到的输入，包含系统约束、工具说明、当前任务、检索出的会话状态和本轮 ReAct 轨迹；记忆是跨步骤或跨请求保存、可在未来按需取回的状态。记忆不等于上下文，只有经过检索、筛选和格式化后注入 Prompt 的记忆才会成为上下文。这个项目把单次执行轨迹作为工作上下文，把论文列表和最近操作论文作为会话记忆，把聊天日志与文件资产作为持久化记录。

#### Q2：每一轮 Prompt 是如何组装的？

**答：** `BaseAgent` 先发现工具并生成工具说明，再把用户任务与当前会话最多 10 篇论文的标题合并，最后追加此前的 `Thought / Action / Observation` 轨迹。每轮重新构造完整 Prompt，模型据此选择一个工具或输出 `FINISH`。三种 Agent 共用这个循环，只替换工具说明、模型响应解析和工具执行通道。

#### Q3：为什么不把完整聊天历史全部塞进 Prompt？

**答：** 完整历史会导致 Token 成本和延迟持续增长，还会把过期信息、重复结果和无关话题带入当前决策。这个项目采用任务型上下文：只注入当前论文快照、最近活动论文和本次最多 5 轮的执行轨迹，不自动回放全部 `chat_logs`。代价是无法直接回答很久以前的开放式对话内容；若有这类需求，应增加摘要或检索层，而不是无限拼接原文。

#### Q4：如何控制上下文窗口和 Token 预算？

**答：** 当前实现通过四个边界控制规模：最多 5 次 ReAct 迭代、最多注入 10 个论文标题、字符串类工具结果最多保留 1,000 字符、步骤日志中的 Observation 最多持久化 4,000 字符。生产环境还应在调用前做 Token 估算，先为模型输出预留预算，再按“系统约束与当前任务、必要工具、相关记忆、历史轨迹”的优先级裁剪；旧轨迹优先摘要，重复工具结果改为句柄或资产 ID。

#### Q5：如何避免上下文污染和 Prompt Injection？

**答：** 不应把工具返回内容当成系统指令。工程上要给“可信指令”和“外部数据”加明确边界，对网页、论文摘要等外部文本做长度和内容限制，并要求模型只从服务端发布的工具集合中选择。更关键的是，安全边界必须落在服务端：校验工具名与参数、覆盖可信 `session_id`、限制文件路径和副作用，而不能只依赖 Prompt 中的“不要执行危险操作”。

### 记忆管理

#### Q6：项目里有哪些层次的记忆？

**答：** 第一层是单次运行的工作记忆，即当前 ReAct `history`；第二层是带 60 分钟 TTL 的会话短期记忆，即 `session_papers` 和 `last_active_paper_id`；第三层是跨重启保留的聊天日志、步骤轨迹、任务和 PDF/翻译资产。需要特别说明：持久化记录不自动等于可用记忆，当前 Prompt 只主动召回论文会话状态，没有把全部历史日志重新注入模型。

#### Q7：“第 1 篇”和“刚才那篇”是如何解析的？

**答：** 搜索结果按 `position` 保存，用户传数字或“第 N 篇”时按 1-based 序号解析；也可以直接传 arXiv ID 或标题子串。对于“刚才那篇”，模型传 `ref = null`，服务端读取 `last_active_paper_id`，再关联当前会话的论文快照。关键点是指代解析由确定性代码完成，模型只表达引用意图，不自行猜测论文 ID。

#### Q8：为什么会话记忆设置为 60 分钟 TTL？

**答：** 这是新鲜度、用户连续操作体验和上下文成本之间的折中。论文列表过期后，`get_last_papers()` 会停止返回；最近活动论文过期后会被惰性清空，从而降低跨任务误引用。当前 TTL 是固定配置，生产环境可以按记忆类型设置不同期限，并在前端明确提示过期，而不是让用户误以为系统仍记得旧对象。

#### Q9：记忆过期或指代失败时怎么办？

**答：** 工具返回明确的“未找到指代对象”或“请先搜索/提供 ID”错误，让 Agent 请求补充信息或重新检索，不能静默选择最相似的一篇。面试中可以强调：错误地执行副作用比多问一次更危险，因此下载、翻译等动作必须在引用唯一解析后执行。

#### Q10：持久化记忆如何保证一致性？

**答：** 当前写入通过 SQLAlchemy 会话和事务完成；一次新检索会替换该 `session_id` 下的论文快照，并在同一提交中更新会话时间。它仍存在同一会话并发请求的“后写覆盖前写”风险。生产级方案可以引入会话级锁、版本号或乐观并发控制，并把 `session_id`、用户身份和租户边界绑定，避免串话和越权读取。

#### Q11：什么时候需要向量数据库或语义记忆？

**答：** 当前状态规模小、引用关系明确，结构化表和确定性查询比向量检索更可控。只有在需要从大量历史对话、论文内容或用户偏好中召回语义相关片段时，才值得增加 Embedding 与向量索引。即使增加，也应结合时间、用户、论文 ID 等元数据过滤，并保留摘要、来源、置信度和删除机制，不能用向量库替代业务主键。

### 工具调用细节

#### Q12：一次工具调用的完整生命周期是什么？

**答：** 流程是“发现工具 → 写入 Prompt → 模型选择工具和参数 → 解析结构化 Action → 校验工具存在 → 服务端覆盖会话参数 → 执行工具 → 归一化 Observation → 写入步骤日志并进入下一轮”。模型负责规划，服务端负责执行与业务不变量；任何模型输出都只是候选调用，不是可信命令。

#### Q13：工具参数是如何约束和校验的？

**答：** 工具注册表提供名称、描述和 JSON Schema，Prompt 用它告诉模型参数类型；执行前还会检查工具名是否在白名单，并对支持 `session_id` 的工具强制覆盖为当前请求会话。当前 `ToolRegistry` 最终主要依靠 Python 函数签名和工具内部校验，尚未统一执行完整 JSON Schema 校验，这是明确的改进点：应在进入工具前做类型、枚举、范围、必填项和额外字段校验，并返回结构化错误码。

#### Q14：模型输出不是合法 JSON 怎么办？

**答：** `regex` 模式先提取严格 JSON，失败后可从文本中有限降级提取工具名和少量参数；无法解析时抛出 `ResponseParseError`，把解析错误作为 Observation 放回轨迹，让模型在剩余轮次自动修正。最后一轮仍失败则以 `ERROR` 结束。生产环境更推荐模型原生 Tool Calling 或受约束解码，减少正则兼容逻辑带来的歧义。

#### Q15：为什么每轮只允许调用一个工具？

**答：** 单工具步骤便于把 Action、Observation、耗时和副作用一一对应，也能让下一步基于真实结果重新规划。它牺牲了无依赖工具的并行度，但本项目主要链路是“搜索后再下载、下载后再翻译”，依赖关系强。若未来支持并行调用，应只并发无依赖、只读或幂等工具，并为每个调用保留独立 ID 和结果。

#### Q16：三种工具调用方案的核心差异是什么？

**答：** `regex` 在当前进程直接调用注册函数，链路短但协议约束较弱；`mcp` 通过 stdio JSON-RPC 发现和调用子进程工具，标准化和隔离更好；`skill_cli` 把能力写进 `SKILL.md`，模型生成受限 CLI，再由子进程执行。三者共用同一个 `BaseAgent`，所以 Benchmark 能在相同任务、模型和业务工具下比较协议开销与稳定性。

#### Q17：MCP 的同步 Agent 如何调用异步 stdio 会话？

**答：** MCP 会话和它所属的 event loop 保持在异步线程中，同步的 `BaseAgent.run()` 放在线程池执行。工具调用时使用 `asyncio.run_coroutine_threadsafe()` 把 `call_tool` 投递回原 event loop，再同步等待结果，超时为 120 秒。这样避免同步 ReAct 循环阻塞负责收发 MCP JSON-RPC 的 event loop。

#### Q18：Skill/CLI 如何防止命令注入？

**答：** 模型输出先由 `shlex.split()` 解析，只识别固定的四个子命令；随后提取 `--key=value` 参数，并从解析后的参数重新构造数组形式命令。执行使用 `subprocess.run(cmd_parts)`，没有启用 `shell=True`，因此模型输出不会直接交给 Shell 解释。生产环境还应增加参数 Schema、路径白名单、最小权限账户和资源配额。

#### Q19：如何处理工具副作用和幂等性？

**答：** 会话状态更新、搜索结果保存和翻译任务创建都集中在 `BaseAgent._execute_with_side_effects()`，避免三种协议各自实现一套副作用。PDF 与翻译资产按 `paper_id` 缓存，已有成功翻译且未指定 `force` 时走 fast path。进一步的生产设计应给副作用调用增加幂等键，在任务表建立唯一约束，并区分“创建成功但响应丢失”和“实际未创建”这两种情况。

#### Q20：工具返回结果很大时如何处理？

**答：** 搜索结果不会把全部论文正文放回 Prompt，而是转换成数量和少量标题；普通字符串 Observation 最多保留 1,000 字符，SSE 步骤预览最多 500 字符，数据库步骤日志最多保存 4,000 字符。更大的结果应落到对象存储或数据库，向模型返回资源 ID、摘要和分页信息，防止上下文爆炸，也避免日志系统承担文件存储职责。

#### Q21：工具失败后会自动重试吗？

**答：** 当前工具异常会被转换为 Observation，模型可以在后续轮次调整参数或选择其他工具；解析错误会自动进入下一轮，但系统没有对所有工具做无差别自动重试。这是有意的，因为副作用工具盲目重试可能重复创建任务。生产环境只应对明确的瞬时错误和幂等操作做有限重试，并结合错误分类、指数退避、抖动和幂等键。

### 超时、取消与长任务

#### Q22：项目当前有哪些超时配置？

**答：** LLM HTTP 请求默认超时 60 秒；Skill/CLI 子进程和 MCP `call_tool` 等待均为 120 秒；PDF 下载使用 10 秒连接超时和 120 秒读取超时；SSE 队列每 15 秒发送一次心跳，这只是保活间隔，不是工具超时。异步翻译已脱离聊天请求，但底层翻译子进程当前没有总墙钟超时，这是需要诚实说明的生产化缺口。

#### Q23：工具超时应该如何设计？

**答：** 应区分连接超时、单次读取超时、单工具总超时和整条 Agent 任务截止时间。入口生成 deadline，每一轮计算剩余预算并向 LLM、MCP、HTTP 和子进程继续传递；工具超时不能超过剩余任务预算。不同工具应按延迟特征配置，而不是统一写死一个值，长任务则应转为异步任务并返回 `task_id`。

#### Q24：超时后应该立即重试吗？

**答：** 先判断调用是否幂等、是否可能已经在服务端成功、错误是否瞬时。只读请求通常可以有限重试；创建任务类调用必须带幂等键并先查询状态；确定性参数错误不应重试。重试要受剩余 deadline 和最大次数约束，并记录每次尝试，避免重试风暴把下游故障放大。

#### Q25：用户取消和系统超时有什么区别？

**答：** 超时是系统预算耗尽，取消是用户主动表达“不再需要”。当前项目用 `run_id` 记录协作式取消，在 LLM 调用前后和工具调用前检查，因此能阻止后续步骤，但不能立即打断一个已经阻塞的同步 LLM 或工具调用。生产级实现应使用可取消的异步客户端，把取消信号传入下游，并对进程执行 `terminate → 宽限等待 → kill` 的清理流程。

#### Q26：如何避免超时后留下僵尸进程或悬挂任务？

**答：** 子进程必须由明确的父生命周期管理，在 `finally` 中关闭管道和会话；超时时先终止进程组，等待短暂宽限期，再强制杀死并回收退出码。MCP stdio 会话应随上下文退出而关闭。后台任务还需要租约、心跳和 watchdog：长时间没有进度就标记 `TIMED_OUT`，重启后扫描并恢复或终结遗留的 `RUNNING` 任务。

#### Q27：为什么翻译任务要异步化？

**答：** 翻译时间远大于普通对话和检索，如果同步等待，会占用 HTTP 连接和 Agent 轮次，也容易触发网关超时。当前设计创建持久化任务后立即返回 `task_id`，后台线程继续执行，SSE 推送进度，成功或失败都写回数据库。这样客户端断线不会丢失任务状态；但当前线程式执行器适合 MVP，生产环境应迁移到独立任务队列和 worker。

#### Q28：SSE 断线会不会导致任务停止？

**答：** 不会。SSE 只是状态通知通道，数据库中的任务状态才是事实来源；翻译后台线程不依赖某个 SSE 订阅者继续存在。客户端重连后应先查询任务状态，再继续订阅增量事件。若要避免事件空窗，还可以给事件加单调递增 ID，并支持 `Last-Event-ID` 补发。

### 可观测性、安全与评测

#### Q29：如何定位 Agent 慢在什么地方？

**答：** 每一步分别记录 `llm_latency_ms` 和 `tool_latency_ms`，任务级再计算总耗时与框架开销，因此可以判断瓶颈来自模型、业务工具还是协议编排。Token 也按步骤和任务累计。生产环境还应统一 `trace_id / run_id / tool_call_id`，记录超时类型、重试次数、下游状态码和队列等待时间，并用分位数而不是只看平均值。

#### Q30：应该记录模型的完整思维链吗？

**答：** 当前项目为了教学和调试保存 `thought`，便于复盘 ReAct 轨迹；生产环境不应依赖或长期保存模型的私有完整推理。更稳妥的做法是记录简短的决策摘要、工具选择原因、结构化 Action、Observation、错误和指标，同时对用户数据、密钥和论文内容做脱敏与保留期限控制。

#### Q31：Agent 在什么情况下结束？

**答：** 正常输出 `FINISH` 时记为 `COMPLETED`；用户停止时记为 `CANCELLED`；执行满 5 轮仍未完成时记为 `MAX_ITERATIONS`；最后一次解析失败或 LLM 异常时记为 `ERROR`。明确终止类型比返回一段自然语言更重要，因为监控、Benchmark 和上层业务都需要区分“答完了”和“被迫停了”。

#### Q32：如何评测工具调用型 Agent？

**答：** 不能只看最终回答文本，还要评估任务完成率、工具选择准确率、参数准确率、调用顺序、无效调用数、迭代次数、终止类型、端到端延迟、LLM/工具/框架耗时和 Token。三种 Agent 必须共享模型、任务集、工具实现和成功判定，只替换协议层，才能把差异归因到调用方式。

#### Q33：如果继续生产化，最优先补什么？

**答：** 第一优先级是统一参数 Schema 校验、错误码、deadline 传递和幂等键；第二优先级是把翻译迁移到持久化任务队列，增加 watchdog、超时回收与崩溃恢复；第三优先级是会话并发控制、鉴权与租户隔离；第四优先级才是更复杂的长期记忆和语义检索。这个顺序先保证调用正确、可恢复和安全，再扩大 Agent 的能力边界。

## 🎯 项目亮点

1. 统一 Agent 内核：新增调用协议时，不需要复制会话、日志、异步任务等业务代码。
2. 可观测性：Thought、Action、Observation、SSE、步骤级耗时均可追溯。
3. 异步工程化：PDF 翻译从对话主链路剥离，用户体验不会被长任务拖住。
4. 多协议实验：不是只实现 MCP 和 Skill，而是用统一 Benchmark 横向验证。
5. 安全边界意识：模型生成命令经过白名单和重构后才执行。
