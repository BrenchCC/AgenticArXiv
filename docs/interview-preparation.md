# AgenticArxiv 面试准备

_围绕项目架构、上下文与记忆、工具调用、超时治理和可观测性的面试问答手册。_

---

## 📋 一句话介绍

AgenticArxiv 是一个面向 arXiv 论文检索、下载与中文翻译的可观测 Agent 工作台。项目重点不只是调用工具，而是将 ReAct 推理循环、工具调用协议、业务状态和评测指标解耦，支持在统一任务集上比较不同 Agent 实现。

## ⚙️ 技术流程

```text
用户自然语言任务
  → FastAPI /chat 接收请求
  → 根据 agent_type 选择 Agent（regex / MCP / skill_cli）
  → BaseAgent 注入会话上下文（已有论文、最近操作论文）
  → 组装 Prompt（任务 + 工具说明 + 历史轨迹）
  → LLM 决策 Thought + Action
  → 服务端校验并执行工具
  → 生成 Observation
  → 持久化轨迹、耗时，并用 SSE 实时推送
  → FINISH / 报错 / 达到最多 5 轮后结束
  → 前端展示结果、论文资产、翻译任务和历史日志
```

业务主链路：

```text
检索论文 → 选择或引用论文 → 下载 PDF → 异步翻译 → SSE 推送进度 → 查看或下载资产
```

翻译不会阻塞聊天。Agent 创建翻译任务后即可结束当前对话；后台任务继续下载、翻译，并通过 SSE 推送进度和最终状态。

## 🔧 三种 Agent 方案


| 方案        | 工具调用方式                          | 面试表达                                                               |
| ------------- | --------------------------------------- | ------------------------------------------------------------------------ |
| `regex`     | LLM 输出 JSON，当前进程直接调用工具   | 最轻量，调用链短，但依赖模型稳定遵守格式                               |
| `mcp`       | 通过 stdio 的 MCP JSON-RPC 调用子进程 | 协议化、工具可发现、隔离更好，但有异步桥接复杂度                       |
| `skill_cli` | LLM 依据 Skill 文档生成受限 CLI 命令  | 工具能力文档化，Token 更低；通过白名单和参数数组避免直接执行模型 Shell |

三种模式只替换工具描述、响应解析和调用通道；ReAct 循环、会话状态、翻译、日志和 SSE 都复用同一个 `BaseAgent`。因此 Benchmark 对比的是协议差异，而不是三套不同的业务实现。

## 💾 数据库字段与设计意图

项目当前使用 SQLAlchemy 管理 7 张核心表。数据库并非只保存最终答案，而是覆盖会话记忆、文件资产、异步任务和 Agent 执行轨迹，使一次任务在服务重启后仍能查询和复盘。

```text
sessions ──< session_papers
    │
    ├──< chat_logs ──< agent_steps
    │
    └──< translate_tasks

session_papers.paper_id ──> pdf_assets.paper_id
                         └─> translate_assets.paper_id
```

这里的关系主要通过业务键 `session_id`、`msg_id` 和 `paper_id` 关联；当前 ORM 没有声明数据库级外键。这让演示版本的表结构与清理逻辑较轻，但生产环境若需要强一致性和级联清理，应增加外键约束、唯一约束与迁移脚本。

### 1. 会话与短期记忆


| 表               | 核心字段                                                                                                   | 设计意图                                                                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `sessions`       | `session_id`、`last_active_paper_id`、`last_active_at`、`updated_at`                                       | 一个会话一条记录；保存最近操作的论文，支持“刚才那篇”的指代。`session_id` 唯一且有索引。                                                            |
| `session_papers` | `session_id`、`paper_id`、`title`、`authors`、`summary`、`pdf_url`、`categories`、`position`、`created_at` | 保存某次检索的论文快照；`position` 让“第 1 篇”可稳定解析，`(session_id, position)` 有联合索引。`authors`、`categories`、`links` 以 JSON 文本保存。 |

会话论文有 60 分钟 TTL。这样可以避免历史论文长期占用 Prompt，也降低用户后续引用到过期搜索结果的概率。

### 2. PDF 与翻译资产


| 表                 | 核心字段                                                                                                                       | 设计意图                                                                                            |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `pdf_assets`       | `paper_id`、`pdf_url`、`local_path`、`status`、`size_bytes`、`sha256`、`downloaded_at`、`error`                                | 每篇论文一份原始 PDF 缓存；`paper_id` 唯一且有索引。`sha256` 用于完整性校验，`error` 保存失败原因。 |
| `translate_assets` | `paper_id`、`input_pdf_path`、`output_mono_path`、`output_dual_path`、`status`、`service`、`threads`、`translated_at`、`error` | 每篇论文一份翻译产物状态；区分单语与双语 PDF，保存翻译服务和线程数，便于复现性能配置。              |

这两张表体现“资产状态”和“任务状态”分离：资产表描述当前可用文件，任务表描述一次后台执行过程。一次翻译失败不会抹去已有的成功资产。

### 3. 异步翻译任务


| 表                | 核心字段                                                                                                                                                     | 设计意图                                                                                                                                                 |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `translate_tasks` | `task_id`、`session_id`、`paper_id`、`status`、`progress`、`input_pdf_url`、`input_pdf_path`、`output_pdf_path`、`meta`、`error`、`created_at`、`updated_at` | 一次翻译请求一条记录。`task_id` 唯一且有索引，`session_id` 有索引，便于按会话查询进度。`progress` 支持 SSE 实时展示，`meta` 用 JSON 文本承载可扩展配置。 |

典型状态流转：`PENDING → RUNNING → SUCCEEDED`；失败时进入 `FAILED` 并写入 `error`。该设计让前端能够先获得 `task_id`，随后独立订阅进度，而不用长时间阻塞 `/chat` 请求。

### 4. 对话与 Agent 轨迹


| 表            | 核心字段                                                                                                               | 设计意图                                                                                                              |
| --------------- | ------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| `chat_logs`   | `msg_id`、`session_id`、`role`、`content`、`model`、`agent_type`、总耗时、Token、`termination_type`、`created_at`      | 保存用户输入和 Agent 最终回复。`msg_id` 唯一且有索引，`session_id` 有索引；Assistant 消息还保存任务级性能与终止原因。 |
| `agent_steps` | `msg_id`、`step_index`、`thought`、`action_name`、`action_args`、`observation`、LLM/工具耗时、单步 Token、`created_at` | 保存一次消息内部的逐步 ReAct 轨迹。`action_args` 为 JSON 文本；步骤级耗时和 Token 用于定位性能与成本瓶颈。            |

`chat_logs` 与 `agent_steps` 通过 `msg_id` 关联：前者回答“用户问了什么、最终答了什么”，后者回答“中间如何决策、调用什么工具、每步花了多久”。

### 5. Token 与终止状态可观测性

运行时累计 `prompt_tokens`、`completion_tokens` 和 `total_tokens`。单步 Prompt/Completion Token 写入 `agent_steps`，任务级 Token 与 `total_time_ms`、`total_llm_ms`、`total_tool_ms`、`framework_overhead_ms` 一起写入 Assistant 对应的 `chat_logs`。同时记录 `COMPLETED`、`CANCELLED`、`MAX_ITERATIONS` 或 `ERROR`，避免只凭最终文本猜测任务是否正常结束。

当前 `/chat` 的响应模型没有直接返回 Token 明细，但日志查询和 Benchmark 可以读取这些字段。后续可将任务级指标加入 `/chat` 响应或单独提供运行详情接口，使前端、日志页和 Benchmark 使用同一指标口径。

## 📚 Prompt 与轨迹记录

每轮 Prompt 的核心结构如下：

```text
你是 AI 研究助手。
可用工具：检索、下载 PDF、异步翻译、查询缓存。
当前任务：{用户任务 + 会话上下文}
要求：
- 每轮只能调用一个工具
- Action 必须是严格 JSON
- 指代“刚才那篇”时使用 ref = null
- 翻译是异步任务，创建后直接 FINISH，不轮询
历史轨迹：
Thought / Action / Observation
```

一次完整执行建议记录以下字段：


| 阶段   | 记录内容                                                |
| -------- | --------------------------------------------------------- |
| 输入   | `session_id`、用户任务、Agent 类型、模型                |
| Prompt | 实际发送 Prompt、工具描述、上下文摘要                   |
| 每一步 | `step_index`、Thought、Action、Action args、Observation |
| 性能   | 单步 LLM 耗时、单步工具耗时、总耗时、框架开销           |
| 成本   | `prompt_tokens`、`completion_tokens`、`total_tokens`    |
| 结果   | 工具调用序列、终止原因、成功或失败、任务与资产 ID       |

## 🔍 真实服务观测样本

测试会话：`interview-trace-20260828`。

- 输入：`检索最近 1 天 cs.LG 方向的论文，最多 1 篇。`
- Agent：`regex`
- 模型：`ep-20260820165946-646cn`
- 结果：成功返回 1 篇论文，并正常 `FINISH`
- 论文：*Learning a Continuous Sepsis Severity Score Without Hour-by-Hour Supervision: A Two-Site Retrospective Study*

真实轨迹：


| Step | Thought / Action                                                                       |  LLM 耗时 | 工具耗时 |
| ------ | ---------------------------------------------------------------------------------------- | ----------: | ---------: |
| 1    | 判断需要检索；调用`get_recently_submitted_cs_papers(max_results=1, days=1, aspect=LG)` |  9,344 ms | 5,563 ms |
| 2    | 判断任务完成；`FINISH`                                                                 | 10,374 ms |     0 ms |

汇总：

- 任务端到端耗时：约 25.3 秒
- LLM 累计耗时：19.72 秒
- 工具累计耗时：5.56 秒
- 工具调用准确：是
- 终止状态：正常 `FINISH`
- SSE：实时收到两条 `agent_step` 事件，与数据库日志一致

这条历史样本生成时，Token 持久化链路尚未补齐，因此无法从旧记录恢复本次真实 Token，不能将缺失值误报为 0。当前版本已经把单步和任务级 Token 写入数据库，但不会反向补全旧数据。

## 🎤 Agent 开发面试问答

以下回答以本项目为例，适合面试时先给结论，再根据追问补充细节。

### 上下文管理

#### 1. 你如何理解 Agent 的上下文？

上下文不只是聊天历史，还包括当前任务、可用工具、工具返回结果、会话状态和终止约束。本项目会把这些信息组合成每轮决策所需的最小上下文，让 Agent 知道已经做了什么、还能做什么以及什么时候应该结束。

#### 2. 为什么不能把全部历史对话都放进 Prompt？

历史越长，Token 成本和延迟越高，噪声也越多，还可能超过模型上下文窗口。更合理的做法是保留当前任务相关信息、最近轨迹和结构化摘要，过期或低相关内容放到外部存储中按需读取。

#### 3. 本项目如何控制上下文长度？

会话只保留近期可引用的论文结果，并设置有效期；ReAct 轨迹按轮次记录，达到最大轮数后结束。生产环境还可以增加历史摘要、按相关性截取 Observation，以及对工具返回结果做字段级压缩。

#### 4. 上下文窗口不足时，你会怎么处理？

先估算 Prompt Token，超过阈值时依次压缩历史、摘要工具结果、删除重复内容，最后才截断低优先级信息。不能直接截断当前任务、工具参数或最近一次 Observation，否则容易造成错误决策。

#### 5. 如何避免工具结果污染后续推理？

工具结果要有明确的来源、结构和边界，并区分“数据”与“指令”。对论文摘要、网页内容等外部文本不能默认信任其中的指令；必要时做字段白名单、长度限制和提示注入过滤。

#### 6. 为什么每轮只允许调用一个工具？

这是一个简单而有效的控制策略：便于校验参数、记录轨迹、定位耗时和重试失败，也能避免多个副作用操作互相影响。需要并行查询时，可以由服务端显式编排，而不是让模型自由产生一串难以控制的调用。

### 记忆管理

#### 7. Agent 的短期记忆和长期记忆有什么区别？

短期记忆服务于当前会话，例如最近检索出的论文和“刚才那篇”的指代；长期记忆跨会话保存稳定偏好或历史知识。两者都应有来源、更新时间和淘汰策略，不能把所有历史数据都当成可靠记忆。

#### 8. 本项目中的“记忆”具体解决什么问题？

它主要解决会话内的指代和连续操作：用户先检索论文，再要求下载或翻译其中一篇时，Agent 可以根据会话中的论文快照和最近操作对象完成解析，而不必重新检索。

#### 9. 为什么保存论文快照，而不是只保存论文 URL？

快照可以稳定支持序号引用和后续复盘，即使远端搜索结果发生变化，也能还原当时用户看到的标题、作者和摘要。URL 仍用于下载，但不应承担全部会话语义。

#### 10. 记忆什么时候应该过期？

取决于业务语义。检索结果属于短期上下文，过期后继续引用可能产生歧义，因此本项目设置了会话级 TTL；用户偏好等长期记忆则需要更长周期，并提供更新、删除和纠错机制。

#### 11. 如何避免记忆之间互相矛盾？

为记忆附加时间、来源和置信度，优先使用当前会话和更近的信息；发现冲突时向用户确认，而不是静默覆盖。对于论文资产，还要以数据库中的状态和完整性校验结果为准。

#### 12. 记忆管理有哪些安全和隐私问题？

只保存完成任务所需的信息，避免无目的记录敏感内容；不同用户和会话必须隔离，并支持删除和过期清理。工具返回的外部文本也不能未经处理直接写入长期记忆。

### 工具调用细节

#### 13. Agent 为什么需要工具，而不是直接回答？

模型擅长理解任务和规划步骤，但不适合凭记忆完成实时检索、文件下载或状态查询。工具把这些能力交给确定性的服务执行，模型负责选择工具、补充参数和解释结果。

#### 14. 如何设计一个好的 Agent 工具？

工具应当职责单一、输入输出清晰、参数可校验、结果可追踪，并明确副作用和失败类型。例如论文检索、PDF 下载、翻译任务创建和缓存查询分别承担不同职责，便于组合和测试。

#### 15. 如何校验模型生成的工具参数？

先校验工具名，再校验参数类型、必填项、取值范围和业务关系；不能因为模型输出了 JSON 就直接执行。解析失败或参数不合法时返回结构化错误，让 Agent 修正，连续失败则结束任务。

#### 16. 为什么不能让模型直接执行 Shell？

模型输出不是可信的执行权限。直接执行会带来命令注入、越权访问和不可控副作用。本项目的工具调用通过受限协议或白名单命令完成，并把参数作为结构化数据传递。

#### 17. regex、MCP 和受限 CLI 三种方式如何取舍？

regex 适合链路短、快速验证的场景，但依赖模型严格输出格式；MCP 更协议化，便于工具发现和进程隔离，但桥接成本更高；受限 CLI 便于复用已有能力和控制 Token，但需要严格的命令白名单。选择应结合安全性、扩展性和运维成本。

#### 18. 工具调用失败后，Agent 应该重试还是换工具？

先判断失败类型。网络抖动、临时限流等可重试错误适合有限次数退避重试；参数错误应修正参数；资源不存在或权限错误通常不应盲目重试。若存在等价工具，可以切换，但要记录原因，避免循环。

#### 19. 如何保证工具调用的幂等性？

查询类工具天然更容易幂等；下载和创建翻译任务要使用业务唯一键或任务 ID 去重，重复请求返回已有结果。这样即使 Agent 重试，也不会重复创建任务或产生多份资产。

#### 20. 工具返回结果应该包含哪些信息？

至少包含成功或失败状态、业务结果、可读错误、可重试标记和追踪信息。长文本应返回摘要或引用 ID，详细内容放在外部存储，避免把大量内容直接塞入下一轮 Prompt。

#### 21. 如何处理工具返回的脏数据？

在工具边界做 schema 校验、字段归一化和必要的去重；缺失关键字段时返回明确错误，不让模型猜测。论文检索结果尤其要统一日期、分类、作者和链接格式。

### 超时与可靠性

#### 22. Agent 系统为什么要设置多层超时？

单一总超时无法区分模型慢、工具慢还是后台任务慢。本项目应分别关注单次 LLM 超时、单次工具超时、Agent 总时限和异步翻译任务时限，并在超时后记录明确的终止原因。

#### 23. 工具超时后应该怎么返回？

立即停止等待并返回可识别的超时 Observation，包含是否可以安全重试。Agent 可以进行有限次重试或向用户说明状态；不能无限等待，也不能把超时误报成业务成功。

#### 24. 为什么翻译任务要异步化？

下载和翻译可能持续较长时间，若阻塞聊天请求，会占用连接并放大超时风险。本项目创建翻译任务后立即返回任务 ID，后台继续执行，前端通过 SSE 获取进度和最终状态。

#### 25. SSE 断开后，任务会不会丢失？

SSE 只负责推送，不应作为任务状态的唯一存储。任务状态和进度先持久化，客户端重连后可以按任务 ID 查询当前状态；即使推送中断，后台任务仍能继续完成。

#### 26. 如何防止 Agent 无限循环？

设置最大迭代轮数、总耗时和重复动作检测；如果连续调用相同工具且 Observation 没有变化，应提前停止并说明原因。本项目把正常完成、达到最大轮数、取消和错误分别记录，便于判断质量问题。

#### 27. 用户主动取消时，应该取消哪些东西？

至少停止当前 Agent 循环和后续工具调用，并把会话标记为已取消。对于已经提交的翻译任务，要根据任务是否支持取消决定是终止后台任务，还是继续执行但不再推送当前会话；两者不能混为一谈。

#### 28. 如何定位一次 Agent 请求变慢的原因？

把总耗时拆成 LLM 耗时、工具耗时和框架开销，并按步骤记录。结合工具调用序列、Token 数、重试次数和 SSE 时间线，可以判断瓶颈是在模型、外部服务、数据库还是事件推送。

### 泛化追问

#### 29. 你如何评价一个 Agent 做得好不好？

不能只看最终文本。还要看任务成功率、工具选择和参数准确率、平均耗时、Token 成本、重试与超时比例、轨迹可解释性，以及是否正确处理失败。项目中的 Benchmark 和持久化轨迹可以支持这些维度的比较。

#### 30. Agent 和传统工作流的边界在哪里？

步骤固定、规则明确的流程应优先使用传统工作流，例如翻译任务状态流转；需要理解自然语言并决定下一步工具的部分适合交给 Agent。本项目将论文检索和用户意图解析交给 Agent，将下载、翻译和状态更新保持为可控的业务服务。

#### 31. 如果让你继续优化这个项目，你会先做什么？

优先完善工具 schema 和错误分类，再补齐超时、重试、幂等和取消语义；之后优化上下文摘要和 Token 预算，最后用统一评测集比较不同 Agent 协议。这样能先提升稳定性，再优化成本和效果。
